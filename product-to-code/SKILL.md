# Product to Code

把业务需求转成代码前，先完成一轮可追踪的对齐。这个 Skill 是通用工作流程；项目规则决定具体能否这样做。

## 规则优先

开始时先读取适用的 `AGENTS.md`、`CLAUDE.md`、README、贡献指南和相关设计文档。

优先级：

1. 系统与安全规则
2. 用户本次明确指令
3. 目标目录中更具体的项目规则
4. 项目正式设计与贡献指南
5. 本 Skill

本 Skill 不覆盖项目的分支、设计评审、测试、Changelog、提交和发布要求。发现冲突时，列出两条规则及来源；能按更具体规则解决就记录采用结果，不能判断时暂停并询问用户。

## 阶段 1：建立项目地图

只读调查，不修改文件。确认：

- 当前仓库、分支、工作区状态和其他 Agent 的改动
- 产品入口和用户可见流程
- 与需求相关的 UI、API、数据、存储、外部服务和测试入口
- 从用户动作到最终副作用的调用链
- 已有能力、缺口、风险和未知问题

输出“事实 / 推断 / 待确认”三栏，并引用文件路径和函数或接口名。

完成标准：能画出本需求的一条端到端调用链，并明确尚未确认的节点；不能用“项目已理解”作为完成标准。

## 阶段 2：澄清业务

将原始描述整理为：

- 用户是谁
- 使用场景是什么
- 当前行为和痛点
- 期望行为
- 成功判据
- 异常、权限、旧数据、刷新、重试和并发边界
- 明确不做什么

对每个缺失规则提出具体选项和影响，不替用户做业务决定。优先问会改变数据、权限、费用、持久化或重试语义的问题。

输出并请求用户确认：

```markdown
# 需求确认单
## 用户场景
## 当前问题
## 期望行为
## 验收标准
## 异常与边界
## 不做范围
## 待确认问题
```

完成标准：每条验收标准都能由用户或测试观察，且待确认问题已得到回答；未确认时停在本阶段。

## 阶段 3：设计

确认需求后，按项目规则创建或更新设计。至少说明：

- 修改模块、文件和职责边界
- 关键接口、数据结构和身份/版本字段
- 调用顺序、状态转换、异步并发、取消和持久化时点
- 失败、恢复、重试、回滚和幂等策略
- 测试场景、真实交互验收和不做范围

先决定最小切片。非 bugfix 按项目规则等待设计评审；bugfix 即使可免评审，也要留下简短设计和验证标准。

完成标准：实施者可仅依据设计找到修改位置、成功判据和失败处理；否则回到调查或澄清阶段。

## 阶段 4：小步实现

一次只实施一个切片。每个切片开始前声明：

- 目标和验收标准
- 允许修改的文件
- 不改变的范围
- 验证命令

实现时遵守项目分支和 worktree 规则，不覆盖其他 Agent 的改动，不顺手重构无关代码。发现设计不成立或范围扩大时先暂停，更新设计并重新确认。

每个切片完成后报告：

```text
已完成：
修改文件：
验证命令及结果：
尚未验证：
剩余风险：
```

完成标准：该切片的代码、测试和局部验收均完成，且每个修改文件都能对应需求或设计。

## 阶段 5：验证与交付

按项目要求运行与改动相称的类型检查、单元测试、lint、构建和真实交互。逐条对照验收标准，区分：

- 已验证的业务行为
- 只被单元测试覆盖的行为
- 尚未验证的环境、模型、Desktop、权限或发布路径

最终报告：

```text
需求结论：
已实现：
未实现：
验收标准逐条结果：
测试与构建结果：
工作区与 diff：
未解决问题：
下一步：
```

测试通过不等于业务完成；没有真实观察到的行为标记为“未验证”。
